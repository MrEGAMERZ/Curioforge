## 1. Problem Statement

A 7–8-year-old has a half-formed idea: *"I want to make something that fizzes — can I use what's on this table?"* They cannot type it fluently, should not be on ChatGPT, and generic kids' AI apps just chat back. They need a safe companion that hears the idea, sees the materials, and turns it into a real activity they can do — then explains the science afterwards.

## 2. What Makes This Cool

Kid taps a big mic, speaks, snaps a photo of household items, and gets a named, personalized **Activity Plan** read aloud — with a *"what do you think will happen?"* pause. They build it, snap the result, and the AI explains what just happened. The screen goes down; something real gets made.

## 3. Landscape Findings

- **Crowded:** voice-first safe chat for kids — Askie, Buddy.ai, LiveGenie, CurioKids, Nano, Pip, Khanmigo, KinderGPT. All do "ask anything, get a warm age-tuned answer."
- **Thin:** camera object ID (SnapCurio, Snap Science, WonderSnap) and household build guides (Kubrio "Hands On" — closest competitor, but text-first and not a full voice loop).
- **EUREKA:** everyone builds the *conversation*. The open wedge is the **closed loop**: speak → snap materials → build → snap result → explain. That is exactly activity-based learning, and it is CURIOFORGE's native shape. Compete there, not on chat.

## 4. Target User and Demo Wedge

- **Primary:** age 7–8 (Grade 2–3), shared family Mac, limited adult supervision, pre-fluent reader.
- **Secondary:** parent/teacher who wants visibility without surveillance.
- **Demo wedge (live at hackathon):** one 5-minute loop on the **SwiftUI macOS app** — voice idea → photo materials → spoken Activity Plan → one Living Canvas prediction → result explanation → safety redirect if they ask for something dangerous.
- Parent/teacher dashboard reads the same core event log behind a parent gate.

## 5. Constraints

- Greenfield: no client/server source exists; `server/src/index.js` is referenced but missing. Phase 0 foundation is unavoidable.
- Existing `gradeBand` is `6-8 | 9-10 | 11-12` — no 7–8 band. Must be added to contracts and docs.
- `RULES.md` locked the stack to React/Vite + Node/Express and forbade native apps; `PRD.md` said text-only/English/grades 6–12. Both are amended by this plan.
- Gemini key stays server-side; LocalStorage / UserDefaults / DataStore only; no accounts, no database, no agent framework.
- Hackathon timeline: one live surface, everything else specified and scaffolded.

## 6. Accepted Premises

1. The product is the **build loop**, not a chat companion.
2. One **shared core** + thin platform shells is the only sane way to serve SwiftUI, Android, and PWA.
3. A **declarative Activity Program** ("bytecode" for interactions) is the portable core IP — emit once, interpret on any OS.
4. Demo live on SwiftUI macOS; Android + PWA scaffolded and phased.
5. All features (Living Canvas, real-time dialogue, multilingual, PWA, dashboard) are planned, sequenced after the demo slice.
6. Safety is deterministic (server guardrail) **plus** prompt-level — never prompt-only.

## 7. Approaches Considered

### Approach A — Native-first triple build
Full SwiftUI + Android + PWA in parallel. Effort XL, risk High.
Pros: all platforms real. Cons: 3× work, no shared core, demo likely broken.

### Approach B — Web-first PWA, native wrappers later
Build React PWA, wrap for macOS/Android. Effort L, risk Med.
Pros: one codebase, fastest. Cons: contradicts the SwiftUI demo requirement; weaker mic/camera on macOS.

### Approach C — Shared core + declarative Activity Program, SwiftUI demo shell **(CHOSEN)**
Node/Express core emits a versioned `ActivityProgram` JSON (blocks: `speak`, `listen`, `showCard`, `askPredict`, `simulate`, `capturePhoto`, `supervisionNote`, `explainResult`, `branch`). Each platform is a thin interpreter. Demo on SwiftUI macOS; Android and PWA interpreters scaffolded in Phase 2. Effort L (demo slice M), risk Med.
Pros: matches the "build for any software" architecture thesis; one AI/safety implementation; demo surface is native-quality. Cons: runtime spec must be designed before clients.

## 8. Recommended Approach

**Approach C.** Build the shared core and the `ActivityProgram` v1 contract first, then the SwiftUI interpreter as the live demo. This gives the judges both the "whoa" and the architecture story.

## 9. Architecture

```
┌─────────────────────────── SHARED CORE (Node/Express, stateless) ───────────────────────────┐
│ /api/session/start   /api/idea/interpret   /api/activity/generate                          │
│ /api/canvas/step     /api/results/explain  /api/safety/check   /api/dashboard/events        │
│  • Gemini wrapper (single call site, x-goog-api-key, 30s timeout, zod validation)           │
│  • Deterministic hazard guardrail + creative-pivot rewriter (before AND after AI)           │
│  • Prompt layer: mentor persona + ageBand 7-8 + locale + safety + no invented citations     │
│  • Emits ActivityProgram v1 + SafetyEvent + DashboardEvent                                  │
└────────────────────────────────────────────────────────────────────────────────────────────┘
                    │ versioned JSON contracts (packages/contracts/v1)
        ┌───────────┼────────────────┬─────────────────────┐
        v           v                v                     v
  SwiftUI macOS   Android        PWA (React/Vite)   Parent/Teacher view
  (demo, live)   (scaffold)      (scaffold)         (parent gate, read-only)
  AVFoundation   CameraX         MediaRecorder      same event log
  Speech/AVSpeech  TextToSpeech  SpeechSynthesis    + safety redirect list
  Canvas + drag  Compose Canvas  SVG/Canvas
```

**ActivityProgram v1** is the portable "bytecode": ordered blocks of `speak`, `listen`, `showCard`, `askPredict`, `simulate {id, params}`, `capturePhoto`, `supervisionNote`, `explainResult`, `branch {on, to}`. Platform shells only render and collect input — no AI logic, no duplicated prompts.

## 12. Success Criteria (demo, ≤5 minutes)

1. Kid speaks an idea → named, personalized Activity Plan appears and is spoken.
2. Photo of materials → plan uses only photographed items.
3. One Living Canvas prediction pause works via touch/voice.
4. Kid snaps result → AI explains the observed science.
5. Dangerous request ("make a fire bomb") → instant safe creative pivot, no refusal wall.
6. Parent gate opens a read-only feed of the session and safety events.
7. No hardcoded responses; all content live from the core.
